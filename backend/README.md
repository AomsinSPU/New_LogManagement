## Schema summary

One user belongs to one tenant. Admin and Viewer are tenant-local roles, not platform-wide roles.
All source events share one normalized `logs` table. UUID primary keys are generated by PostgreSQL.
All timestamps use TIMESTAMPTZ. API inputs/outputs should use RFC3339 with an explicit timezone.

| Table | Purpose / important fields |
| --- | --- |
| tenants | Customer: slug, name, active status, retention_days (minimum 7) |
| users | Tenant-local account: globally unique lowercase email, password_hash, admin/viewer role |
| user_sessions | Browser login sessions: user_id, unique token_hash, expiry, revocation, last_seen_at |
| ingest_keys | Machine ingestion credentials: tenant, key_hash, key_prefix, allowed_sources, creator |
| ingestion_batches | File/batch results: source, submitter/key, status, accepted/rejected counters, errors |
| logs | One normalized event: tenant, event/ingest times, source, event fields, network/actor fields, raw |
| alert_rules | Failed-login threshold configuration: threshold, window, cooldown, severity, enabled |
| alerts | Detected result: rule, IP, count, window, status, evidence snapshot, dedup key |
| schema_migrations | Migration filename and successful application time |

Relationships:

```text
tenants -> users -> user_sessions
tenants -> ingest_keys -> ingestion_batches
tenants -> logs (optional ingest_key and batch references)
tenants -> alert_rules -> alerts
```

### Sessions and ingest keys are different

- Sessions authenticate people using the UI. Store only a token hash, never the raw session token.
- The future backend must generate secure random tokens and validate expiry, revocation,
  idle timeout, and active user/tenant status on requests. Database rows alone do not implement login.
- Use HttpOnly cookies, Secure on HTTPS, appropriate SameSite settings and CSRF protection.
  Persistent login requires both a persistent cookie and an unexpired server session.
- Ingest keys authenticate collectors/scripts and authorize ingestion only, not reading logs or managing rules.
- Determine tenant from verified credentials, never trust the tenant supplied in a request body.
- Show a raw ingest secret only on creation; store its hash. Validate allowed sources in the backend.
- A browser batch has submitted_by; a machine batch has ingest_key_id. Exactly one is required.
- Users should not be moved across tenants without a deliberate workflow revoking existing sessions.

### Logs: four groups of fields

1. Ownership/origin: id, tenant_id, source, ingest_key_id, batch_id, vendor, product, source_event_id.
2. Event: event_timestamp, ingested_at, event_type, event_subtype, severity, action, outcome, message.
3. Participants/network: src_ip/dst_ip, src_port/dst_port, protocol, actor_user, host.
4. Details: metadata JSONB object, raw TEXT, tags array, normalizer_version.

Supported sources: firewall, network, api, crowdstrike, aws, m365, ad.
`actor_user` is a name from an event, NOT a foreign key to application users.
`raw` holds the original record text; `metadata` holds parsed source-specific fields.
Original source event names belong in metadata when normalized event types differ.
IP fields represent individual IPv4/IPv6 hosts, not CIDR subnets. Ports are 0-65535.
Severity is nullable (unknown) or 0-10. Outcome is success, failure or unknown.
Missing source timestamp may use ingestion time with a timestamp_inferred tag; malformed supplied
timestamps should be rejected by validation. Database does not implement normalization.

`search_vector` is generated from message using the simple text search configuration.
Query it with the same configuration, for example plainto_tsquery('simple', ...).
This is token-based message search, not arbitrary substring search of raw/metadata or every language.
Use parameterized SQL and tenant predicates in all future repository queries.

### Constraints and lifecycle

- Composite foreign keys `(tenant_id, referenced_id)` prevent cross-tenant associations
  for creators, keys, batches, alert rules and acknowledging users.
- These constraints DO NOT isolate SELECT results. RLS and backend authorization are not implemented.
- Runtime database role with least privilege is still required. Do not use the initialization superuser
  as the application's production account. RLS with transaction-local tenant context is a follow-up.
- Users/tenants/keys/rules referenced by history are restricted from deletion. Disable/revoke instead.
  Deleting a user cascades its sessions, but history references can still block user deletion.
- Logs reference batches/keys with RESTRICT. Archive/purge parent records only after their logs are gone.
- No FK from alert evidence to logs: evidence remains usable after log retention deletion.
- updated_at is maintained by triggers for tenants, users, alert_rules and alerts.
- Active account checks, Admin/Viewer authorization, ingest-key source permission and consistency
  between a batch's provenance and its log rows must be enforced by the backend.
- error_summary must be an array; metadata/evidence must be objects. The API must cap their sizes,
  raw length, request size, batch size and number of errors recorded.
- A failed batch can contain accepted records if processing stopped early. A partial batch means
  processing finished with both accepted and rejected rows. Complete means all records accepted.

### Alerts and retention

Initial rule: authentication + failure, grouped by tenant and non-null src_ip.
Use ingested_at for the evaluation window (default 300 seconds, threshold 5).
Unique `(tenant_id, dedup_key)` prevents duplicate evaluation results. The worker must construct
deterministic keys and serialize rule/group evaluation to enforce cooldown under concurrency.
Store rule details and limited evidence in alerts. No alert worker or notification sender exists yet.
resolved alerts require resolved_at; acknowledgement records actor and time together.

Retention is based on ingested_at and tenant.retention_days, not the original event timestamp.
Implement bounded batch deletes later. Alerts/batch history need a separate explicit retention policy.
No deletion job, partitioning, automatic retention, or automatic rule execution is installed by these migrations.

## Files and order

Migration directory: `e:\Port\New_LogManagement\backend\db\migrations`

| File | Change |
| --- | --- |
| 000_create_migration_history.sql | History and shared updated_at trigger function |
| 001_create_tenants.sql | Customers |
| 002_create_users.sql | Accounts |
| 003_create_user_sessions.sql | Login sessions |
| 004_create_ingest_keys.sql | Ingestion credentials |
| 005_create_ingestion_batches.sql | Batch results |
| 006_create_logs.sql | Normalized events and generated search vector |
| 007_create_alert_rules.sql | Rule configuration |
| 008_create_alerts.sql | Detected alerts |
| 009_add_search_indexes.sql | Tenant/time/source, failed-login, retention, full-text and alert indexes |

Each migration owns its BEGIN/COMMIT and inserts its history row in the same transaction.
Apply in filename order, with ON_ERROR_STOP enabled. Do not wrap these files in another transaction.
Migrations deliberately fail if applied twice; history is not an automatic skip mechanism.
Do not edit a migration after deployment. Add a new numbered migration instead.
No automatic migration runner, concurrency lock, checksum verification or down migrations exist yet.
Only one operator may apply migrations at a time. Back up a nonempty database before schema changes.

## Apply locally: FIRST RUN ON AN EMPTY DATABASE ONLY

Docker Engine must be running. This command changes the main database; it was not run during implementation.
The database name and user below match the current local Docker setup.

```powershell
Set-Location 'e:\Port\New_LogManagement'
docker compose up -d --wait db
if ($LASTEXITCODE -ne 0) { throw 'Database is not ready' }

foreach ($file in (Get-ChildItem 'e:\Port\New_LogManagement\backend\db\migrations\*.sql' | Sort-Object Name)) {
    Get-Content -Raw $file.FullName | docker compose exec -T db psql -X -U logmanagement_admin -d logmanagement -v ON_ERROR_STOP=1
    if ($LASTEXITCODE -ne 0) { throw "Migration failed: $($file.Name). Stop and inspect history before retrying." }
}

docker compose exec -T db psql -X -U logmanagement_admin -d logmanagement -c 'SELECT * FROM public.schema_migrations ORDER BY version;'
docker compose exec -T db psql -X -U logmanagement_admin -d logmanagement -c '\dt'
```

If execution stops, earlier files remain committed; the failing file is rolled back on connection close.
Check history and apply only unapplied files after resolving the failure. Do not rerun the entire loop.
Do not mount migrations into docker-entrypoint-initdb.d: existing database volumes will not run them.
Never use `docker compose down -v` as a migration/reset workaround on data you want to keep.

## Run schema tests on a disposable database

Tests use synthetic hashes, not usable accounts. They rollback all inserted rows.
The temporary database is removed even if a migration/test fails. No secrets are printed.

```powershell
Set-Location 'e:\Port\New_LogManagement'
$testDb = 'schema_test_' + [Guid]::NewGuid().ToString('N')
docker compose exec -T db createdb -U logmanagement_admin $testDb
if ($LASTEXITCODE -ne 0) { throw 'Cannot create test database' }
try {
    foreach ($file in (Get-ChildItem 'e:\Port\New_LogManagement\backend\db\migrations\*.sql' | Sort-Object Name)) {
        Get-Content -Raw $file.FullName | docker compose exec -T db psql -X -U logmanagement_admin -d $testDb -v ON_ERROR_STOP=1
        if ($LASTEXITCODE -ne 0) { throw "Migration failed: $($file.Name)" }
    }
    Get-Content -Raw 'e:\Port\New_LogManagement\backend\tests\schema.sql' | docker compose exec -T db psql -X -U logmanagement_admin -d $testDb -v ON_ERROR_STOP=1
    if ($LASTEXITCODE -ne 0) { throw 'Schema tests failed' }
} finally {
    docker compose exec -T db dropdb -U logmanagement_admin $testDb
    if ($LASTEXITCODE -ne 0) { throw "Cleanup failed; remove temporary database $testDb manually" }
}
```

Use only in development/demo databases AFTER all ten migrations. Never automatically seed production.

| Data | Total |
| --- | --- |

Sources: firewall, network, api, crowdstrike, aws, m365, ad. Each batch's accepted_count matches
its actual records. Batches represent browser uploads, so submitted_by is set and ingest_key_id is null.
The separate revoked keys demonstrate credential records without authorizing ingestion.
All IPs/accounts/events are synthetic. These records demonstrate the normalized schema; they are NOT
real vendor payload samples and do not prove ingestion, normalization, login or alert workers work.

Security: password_hash/token_hash/key_hash contain explicit disabled fixture markers, NOT usable hashes.
No real credentials are seeded. All users are inactive, keys revoked and sessions expired/revoked.
There is no demo login password. When auth is implemented, provision real hashes using its chosen
algorithm and activate accounts explicitly; do not treat these markers as valid authentication data.
Email addresses: admin-a@demo.invalid, viewer-a@demo.invalid, admin-b@demo.invalid, viewer-b@demo.invalid.

Stable deterministic UUIDs identify fixtures (MD5 is used ONLY for predictable fixture IDs, not credentials).
Re-running uses ON CONFLICT(id) DO NOTHING: no duplicate rows, no overwrite of edits, no password resets,
and no reactivation. Other unique-key collisions fail and roll back instead of adopting unrelated rows.
Do not use these reserved IDs for application data. This is an initial-data seed, not a repair/reset tool.
If demo rows are manually modified/deleted, assertions may fail; use a fresh disposable demo database.
Initial event times are relative to the first run; repeat runs do NOT refresh timestamps. Old demo events
can age out of a dashboard or retention window. Seeded alerts are fixtures, not worker-generated alerts.
